wav2flac benchmark

Encodes the same WAV on the main thread (encode() / encodeSync()) and in a Web Worker, and compares timing, memory and how long the page freezes.

What is measured

  • Worker vs. no worker. "Worker" is a dedicated Web Worker (createWorkerEncoder()). An AudioWorklet isn't used: it runs on the real-time audio thread with 128-frame render quanta and is meant for playback, not batch encoding.
  • Encoder input. "WAV file" encodes the WAV bytes. The raw PCM inputs encode the same samples without a header, via the pcm option: as integer typed arrays (Int16Array, or bytes for 24-bit), or as a Float32Array like Web Audio delivers, converted back to the source bit depth. The conversion from the WAV happens before timing. MB/s and the output ratio refer to the input actually passed, so a Float32Array of 16-bit audio is twice the bytes.
  • Other libraries. libav.js (FFmpeg's FLAC encoder, in its own worker) and libflac.js (libFLAC, on the main thread) get the same samples as integer PCM, prepared before timing. Any conversion a library needs on top of that is timed. They don't transcode.
  • Timing covers one encode call with the input already in memory. Worker runs include transferring the input to the worker; the worker is started once per mode, and its start-up time is listed separately.
  • Longest block is the longest gap between 1 ms timer ticks on the page's main thread. That's how long the page couldn't respond. Browsers clamp timers to about 4 ms, so smaller values are noise.
  • Max RSS (peak resident memory) isn't observable from a web page. Choose "Node (server)", or run npm run bench:browser: its Playwright driver reads the renderer process's peak RSS from /proc. In the browser you get wasm memory, Chrome's JS heap (performance.memory) and measureUserAgentSpecificMemory(). That last one needs cross-origin isolation, which the bench server provides.
